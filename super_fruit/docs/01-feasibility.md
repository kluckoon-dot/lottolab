# 슈퍼프룻 타당성 검토

작성일 2026-09-10 · 검토 대상: 생생보감 농산물 수익화 관제센터

---

## 한 줄 결론

**만들 수 있다. 네이버 쪽은 생각보다 멀쩡하고, 진짜 급한 건 우리 코드 안에 있는 버그다.**

기술적으로 못 만들 건 거의 없다.
네이버 API는 **종료가 아니라 클라우드(API 허브)로 이관**됐고, 실제로 끊긴 건 **쇼핑 검색 API 하나**뿐이다.
남은 위험은 세 개인데, 그중 제일 급한 건 외부 요인이 아니라 **카테고리 ID 버그**다.
그리고 농산물이라서 열리는 대체 경로(KAMIS)가 하나 있는데, 그게 오히려 원래 목표보다 낫다.

---

## 검토 전제 — 먼저 밝힌다

- **실제 코드를 못 봤다.** 코드는 `C:/Users/kluck/Downloads/...` 로컬에 있고 이 저장소엔 없다.
  그래서 "화면·테스트 163개 통과·버전 71" 같은 건 전부 **이전 어시스턴트의 진술**이지 내가 확인한 사실이 아니다.
  아래 판정은 **기획·외부 조건 기준**이다. 코드 품질 판정이 아니다.
- 반면 **네이버 API 상태와 약관, 대체 데이터 소스는 내가 직접 조사했다.** 근거 링크는 문서 하단.

## 치명적 리스크 3개

### 리스크 1 — 네이버가 문을 닫고 있다 (제일 큼)

이전 대화에서는 "쇼핑검색 API 종료" 하나만 잡았는데, 실제로는 **세 겹**이다.

> **2026-09-10 정정.** 초판에서 이관과 종료를 뭉뚱그렸다. 둘은 다르다. 아래가 수정본이다.

**① 검색어트렌드·쇼핑인사이트 — 종료 아님. 이관이다.**
2026-06-25 출시된 **NAVER API HUB**(네이버 클라우드 플랫폼)로 옮겨갔다.
- 검색 API(블로그·뉴스·이미지·지역·지식iN·백과·카페·웹문서), **쇼핑인사이트**, **검색어트렌드** 제공
- 키 하나로 통합, **종량제**, 현재 **한시적 무료** (유료 전환 시 사전 공지)
- 기존 개발자센터 인증키는 **2027-06-30까지 유효**

→ 죽는 게 아니라 **이사**다. 오히려 정식 상품이 됐으니 안정성은 올라갔다.
할 일은 "대체재 찾기"가 아니라 **"2027-06-30 전에 허브로 키 갈아끼우기"**다. 난이도 낮다.

**② 쇼핑 *검색* API — 여기만 진짜 종료다**
이게 예외다. **쇼핑인사이트와 쇼핑검색은 다른 API**다.

| | 주는 것 | 상태 |
|---|---|---|
| 쇼핑**인사이트** (데이터랩) | 카테고리·키워드별 **클릭 추세**, 기기·성별·연령 | **허브에 있음. 생존** |
| 쇼핑**검색** (검색 API) | **상품 목록·가격·상품수** | **2026-07-31 종료** |

허브가 홍보문구에 쓰는 "쇼핑"은 쇼핑**인사이트**다. 공개된 허브 API 목록에 쇼핑·책·전문자료 **검색**은 없고,
보도도 이 셋은 2026-07-31 완전 종료·대체 없음으로 일치한다.

→ 그래서 **클릭 추세·기기·성별·연령은 다 살아있고, 상품 가격·상품수 원본만 없다.**
평균가격 카드를 버린 판단은 여전히 **맞았다.** 다만 이유는 "네이버가 다 닫아서"가 아니라
"쇼핑검색 API 하나가 닫혀서"다. 나머지는 멀쩡하다.

> **최종 확인은 콘솔에서.** 허브 콘솔에 로그인해 실제 API 목록을 눈으로 보는 게 제일 확실하다. → 확인 필요

**③ 약관 개정 — 3일 전 시행됐다 (2026-09-07)**
이게 제일 안 좋다. 개정 검색 API 특약의 금지 행위에 이런 게 들어갔다.

- **데이터 복사·저장·캐싱 금지**
- 제3자 제공·판매 금지
- AI 입력·학습·평가·노출 활용 금지
- **API 활용 수익화 금지**
- 서버 보관은 이력 조회 목적 **최대 21일**
- 가공 없이 노출, 출처 표시와 원본 링크 제공 의무

API 허브에는 **2026-09-20부터** 개정 약관이 적용된다.

**뭐가 문제냐면** — 이 대시보드의 핵심 가치가 정확히 "네이버 데이터를 긁어서 우리 DB에 쌓고, 3년 추세로 가공해서, 자체 판정 지표를 만드는 것"이다.
**21일 서버 보관 제한과 3년 누적 추세 차트는 정면으로 충돌한다.**

다만 과장은 안 할게. 짚어둘 것:
- 이 특약이 **검색어트렌드·쇼핑인사이트에도 동일하게 적용되는지는 원문 확인이 필요하다.** 기사만으로는 단정 못 함. → **확인 필요**
- **검색광고 API는 별개 서비스**다. 광고주 본인 계정 데이터를 본인이 조회하는 구조라 이 특약 대상이 아니다.
- 사이트가 **비공개·소유자 전용**이라는 게 지금은 방패다. 공개하거나 서비스로 파는 순간 "수익화 금지"에 정면으로 걸린다.

**→ 그래서 판정: 내부 의사결정 도구로 혼자 쓰는 건 계속 가능. 공개·판매·외부 제공은 패스.**
이 선을 넘을 계획이 있으면 지금 설계를 바꿔야 한다.

### 리스크 2 — 카테고리 ID 버그. 이미 모은 데이터 상당수가 쓰레기다

포도·멜론·배 등이 전부 `50000006`(식품 상위 기본값)으로 저장돼 있다는 건
**타당성 문제가 아니라 그냥 버그**인데, 파급력이 크다.

쇼핑인사이트는 카테고리 단위로 클릭추세·기기·성별·연령을 준다.
카테고리가 죄다 "식품"이면 나온 숫자는 포도 데이터가 아니라 **식품 전체 데이터**다.
지금 쌓인 쇼핑 1,400건 중 상당수가 **재수집 대상**이라고 봐야 한다.

**이거 안 고치고 수집률 100% 채우는 건 의미 없다.** 쓰레기를 열심히 모으는 것뿐이다.
→ **최우선 순위 1번.**

### 리스크 3 — 온그린 표는 전부 미검증이다

이전 대화의 온그린 기능표(발주 가능/결제 가능/…)는 그럴듯한데,
같은 답변 안에 **"발급된 Access Key 0개"** 라고 적혀 있다.

즉 **단 한 번도 실제로 호출해본 적이 없다.** 저 표는 100% 문서 읽고 만든 추정이다.
어드민플러스가 협력사 Open API를 기본 제공하는 건 맞지만, 업체별로 부여 권한이 다르다는 건 그쪽도 인정했다.

**표를 믿고 발주·결제 코드부터 짜면 안 된다.** 키 발급 → 실호출 한 번 → 그다음이 순서다.

## 이번 검토 최대 수확 — 평균가격, 안 버려도 된다

평균가격 카드를 버린 이유는 "네이버에 시장 가격 원본이 없어서"였다. 그 판단 자체는 맞다.
**그런데 이건 농산물이다.** 네이버 말고 다른 데 있다.

**KAMIS(농산물유통정보, 한국농수산식품유통공사)** — Open API 제공.

- 전국 **도매 5개 도시 16개 시장 / 소매 19개 도시 54개 시장**
- 도매 69품목 116품종 / 소매 90품목 143품종, 등급 2단계
- **1996년부터 현재까지 일별 가격**, 주말·공휴일 제외 매일 조사
- 공공데이터포털에도 일별 도·소매 가격정보 조회 API 등재
- API 키 신청 필요, 공공데이터라 상업적 활용·저장 제약이 네이버보다 훨씬 느슨함

**이게 왜 중요하냐** —
이전 대화에서 평균가격 카드에 이런 면책을 달아야 한다고 했다.

> "시장 전체 평균·실거래 평균단가는 아닙니다."

**KAMIS는 정확히 그 실거래 평균단가다.** 면책을 달 필요가 없는 진짜 시세다.
게다가 농산물 kg 단가 문제(1kg vs 5kg 혼재)도 KAMIS는 규격·등급을 나눠서 주니까 자연스럽게 풀린다.

**→ 판정: 평균가격 카드는 부활시켜라. 단 네이버 표본 평균이 아니라 KAMIS 실거래 시세로.**
그러면 화면 문구가 이렇게 바뀐다.

```
샤인머스캣 도매 평균  12,400원/kg   (▼3.2% 전주비)
가락시장 외 15개 도매시장 · 상품(上) 등급 · 2026-09-09 조사
출처: KAMIS 농산물유통정보
```

면책 문구보다 이게 훨씬 세다. **그리고 이게 형이 실제로 장사할 때 필요한 숫자다.**
"네이버에서 얼마에 팔리나"보다 "도매에서 얼마에 떼오나"가 마진 계산에 직결되니까.

여기에 온그린 공급가를 붙이면 **KAMIS 도매시세 ↔ 온그린 공급가 ↔ 우리 판매가** 3단 비교가 된다.
이게 원래 만들려던 것보다 좋다.

## 그래서 살릴 것 / 버릴 것 / 바꿀 것

**살릴 것**
- 검색광고 API 기반 지표 전부 (월검색수·클릭수·CTR·입찰가·광고깊이) — 제일 안정적인 축
- 탑다운 품목 탐색, 경쟁강도 구간, 연관키워드
- NAVER 원본 / 승인값 배지 분리 — 좋은 설계다. 소스가 늘어날수록 더 중요해진다

**버릴 것**
- **ItemScout 완전 동일성 목표.** 원천이 다른데 같은 숫자가 나올 리 없다.
  ItemScout는 자체 수집·자체 추정이다. "확인 불가"가 아니라 **"불가능"**이 맞는 판정이다.
  비교 기준은 ItemScout가 아니라 **우리 원본의 출처와 관측일**이어야 한다.
- 매출·판매량 잔존 필드·가져오기 코드 — 되살아날 일 없다. 지우는 게 맞다
- 결제 자동화 구상 — 최소 6개월 뒤 얘기

**바꿀 것**
- 평균가격 → **KAMIS 실거래 시세로 부활**
- 데이터 보관 설계 → 21일 조항 확인 후, 걸린다면 **네이버 원본은 단기 보관 + 파생 지표만 장기 보관** 구조로 분리
- 검색어트렌드·쇼핑인사이트 → **API 허브로 키 교체. 데드라인 2027-06-30** (종료 아님, 이사다)

1번 끝나면 하루 1,400회 × 3서비스로 **2~3일이면 한 바퀴 돈다.** 급한 일이 아니다.
