# 1순위 — 카테고리 ID 버그 잡기

## 지금 무슨 일이 일어나고 있나

쇼핑인사이트는 **카테고리 단위**로 데이터를 준다. "포도"라는 키워드를 넣어도
카테고리를 `50000006`(식품)으로 보내면 네이버는 **식품 전체의 클릭 추세**를 돌려준다.

지금 포도·멜론·배가 전부 `50000006`이다. 그러니까

```
포도의 연령 구성  = 식품 전체의 연령 구성
멜론의 기기 구성  = 식품 전체의 기기 구성
배의 클릭 추세    = 식품 전체의 클릭 추세
```

**세 품목의 숫자가 사실상 똑같이 나오고 있다는 뜻이다.** 이게 검증 방법이기도 하다.

## 검증 먼저 (5분)

고칠 결심 하기 전에 이것부터 확인해라.

1. 대시보드에서 **포도 / 멜론 / 배**의 연령 구성 그래프를 나란히 띄운다
2. 셋이 거의 같으면 → 버그 확정
3. 셋이 뚜렷이 다르면 → 내 진단이 틀렸다. 여기서 멈추고 다시 보자

품목 특성상 배(제수용·중장년)와 멜론(선물용)의 연령 구성이 같을 수가 없다.
같게 나오면 그건 데이터가 아니라 배경 잡음이다.

## 진짜 카테고리 ID 구하는 법

네이버는 카테고리 목록 API를 따로 주지 않는다. **수동으로 캐야 한다.**

**방법 A — 네이버쇼핑 URL에서 (제일 확실)**
1. `shopping.naver.com` 접속
2. 식품 → 농산물 → 과일 → 포도 순으로 카테고리를 타고 들어간다
3. 주소창 URL의 **`catId=` 값**이 그 카테고리의 ID다
4. 품목마다 반복해서 표로 적는다

**방법 B — 데이터랩에서 교차 확인**
1. `datalab.naver.com/shoppingInsight/sCategory.naver` 접속
2. 분야 선택창에서 같은 카테고리를 고른다
3. 여기서 잡히는 코드가 방법 A의 `catId`와 같은지 대조한다

**두 방법이 다르면 API에 넣을 값은 데이터랩 쪽이다.** 쇼핑인사이트 API가 쓰는 체계니까.

> 카테고리 depth 제한이 있을 수 있다. 너무 깊이 들어간 소분류는 API가 안 받을 수 있으니
> 첫 호출로 확인해라. → **확인 필요**

## 만들 것 — 매핑 테이블

```
data/category-map.json

{
  "포도":       { "catId": "5000____", "depth": 4, "verifiedAt": "2026-09-__" },
  "샤인머스캣": { "catId": "5000____", "depth": 4, "verifiedAt": "2026-09-__" },
  "멜론":       { "catId": "5000____", "depth": 4, "verifiedAt": "2026-09-__" },
  "배":         { "catId": "5000____", "depth": 4, "verifiedAt": "2026-09-__" }
}
```

`verifiedAt`을 꼭 넣어라. 네이버 카테고리는 개편된다. 언제 확인한 값인지 남겨야 나중에 안 헤맨다.

## 제일 중요한 규칙 — fallback을 없애라

지금 코드는 매핑 실패 시 `50000006`으로 떨어뜨린다(`signals/route.ts:848`).
**이게 근본 원인이다.** 조용히 틀린 값을 만들어내는 구조다.

```
바꾸기 전:  매핑 없음 → 50000006 으로 조회 → 엉뚱한 데이터 저장
바꾼 뒤:    매핑 없음 → 수집 스킵 → status: "unmapped" 로 기록
```

**틀린 데이터를 만드느니 빈칸이 낫다.** 화면에는 "카테고리 미매핑 N건"으로 노출해서
매핑 작업이 얼마나 남았는지 보이게 해라.

## 오염 데이터 격리

기존 행을 **지우지 마라.** 증거로 남긴다.

1. 쇼핑인사이트 저장 행 중 `categoryId = 50000006` 인 것 전부 `invalid: true` 플래그
2. 화면·판정 로직에서는 제외
3. 재수집 큐에 다시 투입

## 재수집

- 매핑 완료된 품목만 큐에 넣는다
- 하루 1,400회 × 3서비스면 **2~3일이면 한 바퀴** 돈다. 안 급하다
- 1,400이 자체 설정값인지 네이버 실제 한도인지 확인해라. 자체값이면 상향 여지가 있다

## 끝난 뒤 확인

다시 포도 / 멜론 / 배 연령 구성을 나란히 본다. **이제 달라야 정상이다.**
안 달라지면 카테고리 ID가 여전히 틀렸거나 API 파라미터가 안 먹은 거다.

## 로컬 세션에 그대로 붙여넣을 지시문

```
쇼핑인사이트 카테고리 ID 버그를 잡아줘.

문제: app/api/signals/route.ts:848 의 fallback 로직이 카테고리 매핑에 실패하면
50000006(식품 상위)으로 떨어뜨린다. 그래서 포도·멜론·배가 전부 식품 전체
데이터를 받아 저장하고 있다.

작업:
1. 먼저 signals/route.ts:848 주변을 읽고 현재 fallback 경로를 정확히 설명해줘.
   내가 파악한 게 맞는지 확인부터.

2. data/category-map.json 을 새로 만들어줘. 품목명 → { catId, depth, verifiedAt }
   구조. 값은 내가 채울 거니까 빈 스켈레톤으로.

3. fallback을 제거해줘. 매핑이 없으면 50000006으로 조회하지 말고
   수집을 스킵하고 status "unmapped" 로 기록. 조용히 틀린 값을 만드는 경로를
   완전히 없애는 게 목적이다.

4. 기존 쇼핑인사이트 저장 행 중 categoryId = 50000006 인 것을 삭제하지 말고
   invalid: true 로 플래그하는 마이그레이션을 만들어줘. 화면과 판정에서는 제외.

5. 대시보드에 "카테고리 미매핑 N건" 표시를 추가해줘.

6. 재수집 큐가 invalid 플래그된 행만 다시 태우도록 해줘.

주의: 카테고리 ID를 추측해서 채우지 마. 모르면 빈칸으로 두고 나한테 물어봐.
```

# 2순위 — KAMIS 붙이기

## 왜 이게 값싼 승리인가

버린 평균가격 카드를, 면책 문구 없는 **실거래 시세**로 되살린다.
코드 변경량은 적고 화면 가치는 크다.

## 절차

**① 키 발급**
1. `kamis.or.kr` → 고객센터 → Open-API → 이용안내
2. 이용 신청 → **인증키 + 인증 아이디** 발급 (두 개 다 나온다)
3. 발급까지 걸리는 시간은 확인 필요. 즉시가 아닐 수 있다

**② 보험으로 공공데이터포털도 같이 신청**
- 공공데이터포털의 [일별 도·소매 가격정보 조회 API](https://www.data.go.kr/data/15156057/openapi.do)
- 같은 aT 데이터인데 창구가 다르다. 한쪽이 막히거나 스펙이 안 맞을 때 대비

**③ 첫 호출 — 여기서 승부가 갈린다**

가장 먼저 확인할 건 응답 형식이 아니라 **품목 커버리지**다.

```
확인 순서
1. 품목 코드 목록을 받아온다
2. 우리 4,041개 키워드 중 몇 개가 매칭되나 센다
3. 특히 "샤인머스캣"이 독립 품종으로 있는지 본다
```

**여기서 솔직하게 짚고 갈 것** — KAMIS 커버리지는 도매 69품목 116품종, 소매 90품목 143품종이다.
우리 키워드는 4,041개다. **매칭률은 한 자릿수 퍼센트일 가능성이 높다.**

그래서 KAMIS는 **전 키워드용이 아니라 주력 품목 20~30개용**으로 봐야 한다.
샤인머스캣이 "포도"로만 잡히고 품종 구분이 없으면 가치가 한 단계 떨어진다.
**이걸 첫 호출로 먼저 확인하고, 그 결과 보고 투자 규모를 정해라.**

**④ 붙이기**
- 새 소스로 `source-registry.json`에 등록 (온그린 옆에)
- 배지는 `KAMIS 실거래`로 — NAVER 원본 / 승인값과 구분되게
- 캐시 주기는 일 1회면 충분하다. KAMIS는 주말·공휴일 제외 매일 조사다

**⑤ 화면**
```
샤인머스캣 도매 평균  12,400원/kg   (▼3.2% 전주비)
가락시장 외 15개 도매시장 · 상품(上) 등급 · 2026-09-09 조사
출처: KAMIS 농산물유통정보
```
네이버와 달리 공공데이터라 저장·가공 제약이 훨씬 느슨하다.
**21일 보관 제한 걱정 없이 장기 시계열을 쌓을 수 있는 유일한 축이다.** 이게 진짜 이점이다.

## 로컬 세션 지시문

```
KAMIS 농산물유통정보 Open API를 붙일 준비를 해줘.

목표: 삭제했던 평균가격 카드를 KAMIS 도·소매 실거래 시세로 되살린다.

작업 순서:
1. KAMIS Open-API 문서를 읽고 일별 도·소매 가격 조회 엔드포인트의
   실제 파라미터명과 응답 스키마를 정리해줘. 추측하지 말고 문서 기준으로.

2. 우리 키워드 목록과 KAMIS 품목·품종 코드의 매칭률을 먼저 계산해줘.
   특히 샤인머스캣이 독립 품종으로 존재하는지 확인. 이 결과 보고
   얼마나 투자할지 정할 거다.

3. source-registry.json 에 KAMIS를 새 소스로 등록. 배지는 "KAMIS 실거래"로
   NAVER 원본·승인값과 구분되게.

4. 일 1회 캐시. 주말·공휴일은 조사가 없으니 직전 영업일 값으로 폴백하되
   화면에 조사일자를 반드시 표시.

주의: 카테고리 버그 작업이 끝난 뒤에 시작해. 그리고 매칭률이 낮게 나오면
      그대로 보고해줘. 억지로 매칭하지 마.
```

# 순서 요약

```
1. 포도/멜론/배 연령 구성 비교        →  버그 확정 (5분)
2. 네이버쇼핑에서 catId 캐기          →  30분~1시간, 수동
3. fallback 제거 + 매핑 테이블         →  로컬 세션
4. 오염 데이터 invalid 플래그          →  로컬 세션
5. 재수집                              →  2~3일 자동
6. 포도/멜론/배 다시 비교              →  이제 달라야 정상
─────────────────────────────────────
7. KAMIS 키 신청                       →  대기 발생 가능, 지금 같이 걸어둬도 됨
8. 품목 매칭률 확인                    →  여기서 투자 규모 결정
9. 평균가격 카드 부활
```

**7번은 지금 바로 신청 걸어둬라.** 발급 기다리는 동안 1~6번 하면 시간이 안 겹친다.
