# 아이템스카우트와 우리 수치 대조

2026-09-14 · 사용자가 올린 아이템스카우트 "고구마 연관키워드" PDF(49개) 기준

## 1. 검색수 — 문제 없다

같은 키워드 29개를 맞대어 보았다.

| 키워드 | 아이템스카우트 | 우리 | 차이 |
|---|---|---|---|
| 김의준고구마 | 13,110 | 12,870 | -2% |
| 해남고구마 | 5,890 | 5,530 | -6% |
| 토울고구마 | 4,040 | 3,980 | -1% |
| 해들녘고구마 | 1,360 | 1,360 | 0% |
| 강화도고구마 | 710 | 710 | 0% |

**29개 중 27개가 오차 10% 이내, 차이 중앙값 0.0%.**
남은 차이는 수집 날짜가 달라서다. 둘 다 같은 네이버 검색광고 API 를 쓴다.

## 2. 경쟁강도 — 아예 다른 지표다

PDF 에서 공식을 역산했다.

```
경쟁강도 = 상품수 ÷ 검색수
```

48개 전부 이 식과 일치했다(100%).

| 키워드 | 상품수 | 검색수 | 계산 | 표기 |
|---|---|---|---|---|
| 김의준고구마 | 386 | 13,110 | 0.029 | 0.03 |
| 해남고구마 | 5,061 | 5,890 | 0.859 | 0.86 |
| 토울고구마 | 741 | 4,040 | 0.183 | 0.18 |

우리 경쟁강도는 전혀 다른 것이다.

```
우리 = 0.55 × (광고깊이/15) + 0.45 × (1위입찰가/2500),  0~10 으로 환산
```

**상품수 원본이 없어서 만든 대용품이다.** 쇼핑검색 API 가 2026-07-31 종료됐다.
값의 크기도 뜻도 다르므로 아이템스카우트 수치와 나란히 놓고 비교하면 안 된다.

## 3. 의도 분류 — 우리 분류는 맞았다

아이템스카우트가 쇼핑성이라 한 29개를 우리도 **29개 전부 쇼핑성**으로 봤다.
우리 고구마 키워드 412개 중 402개가 쇼핑성이다.

"정보성처럼 보인다"는 인상의 실제 원인은 분류가 아니라 **정렬**이다.
검색량 순으로 세우면 요리 키워드가 위로 온다.

```
고구마줄기볶음 116,440   고구마줄기김치 55,300   고구마순김치 45,590
고구마순볶음 35,050      고구마맛탕 14,140      고구마에어프라이어 14,530
```

아이템스카우트 목록에는 이것들이 없다. 그쪽은 **대표카테고리:고구마** 로 걸렀기 때문이다.
대표카테고리는 그 키워드로 실제로 팔리는 상품의 카테고리이고, 쇼핑 검색 결과를 봐야 안다.
우리는 그 데이터가 없어 키워드 글자로만 묶는다. 그래서 요리 키워드가 같이 들어온다.

광고 신호로 가를 수 있는지도 재보았다. 안 된다.

```
아이템스카우트 쇼핑성 29개   광고깊이 7.03 · 1위입찰가 2,325원 · 입찰가있음 100%
요리 어미 968개              광고깊이 6.08 · 1위입찰가 1,236원 · 입찰가있음  91%
```

고구마줄기볶음도 광고깊이 7 에 입찰가 400원이다. 광고주가 레시피 키워드에도 붙는다.

## 4. 그래서 막힌 곳은 하나다 — 상품수

상품수만 있으면 세 가지가 한 번에 풀린다.

1. 경쟁강도를 아이템스카우트와 같은 식으로 계산
2. 대표카테고리 추정 (상품이 몰린 카테고리)
3. 요리 키워드 걸러내기 (상품수가 검색수에 비해 터무니없이 적은 것)

쇼핑검색 API 가 종료됐지만 API HUB 로 이관됐을 가능성이 남아 있다.
검색어트렌드가 `/search-trend/v1/search`, 쇼핑인사이트가 `/shopping/v1/...` 로 살아 있었다.
쇼핑검색도 같은 게이트웨이에 있는지 확인해야 한다. → 확인 필요

## 상품수 확보 시도 (2026-09-14)

경쟁강도 = 상품수 ÷ 한달 검색수. 48/48 키워드로 아이템스카우트와 대조해
식을 확정했다. 검색수는 우리가 이미 갖고 있으니 남은 건 상품수 하나다.

### 18단계 — 자리 찾기 (`fetch-hub.mjs --shop-count`)
없는 경로가 뭘 돌려주는지 대조군으로 먼저 재고, 그것과 다른 응답만 본다.
두 호스트에 12개 후보를 시험 키워드 하나로 훑는다.

- API HUB (`naverapihub.apigw.ntruss.com`, NCP 헤더)
  `/search/v1/shop` · `/search/v1/shop.json` · `/search/v1/shopping` ·
  `/shopping/v1/search` · `/shop/v1/search` · `/shopping-search/v1/search` ·
  `/shopping/v1/shop` · `/search-shop/v1/search` · `/commerce/v1/search` ·
  `/v1/search/shop.json`
- 옛 개발자센터 (`openapi.naver.com`, X-Naver-Client-Id/Secret)
  `/v1/search/shop.json` · `/v1/search/shop`

이관 규칙이 `/v1/search/news.json` → `/search/v1/news` 였으니
`/search/v1/shop` 이 제일 유력하다. 응답에 `total`/`totalCount`/`result.total`
중 하나라도 있으면 적중으로 보고 `naver-out/hub-shopcount.json` 에 적는다.

주의: 이 세션의 키는 NCP API HUB 키다. 옛 주소 쪽이 200을 주려면
developers.naver.com 애플리케이션 키가 따로 있어야 한다.

### 19단계 — 전부 채우기 (`--shop-count-all`)
주소를 `hub-shopcount.json` 에서 읽는다. 목표 목록은 16b 가 떨구는
`naver-out/section-keywords.txt` — 화면이 실제로 쓰는 키워드만, 검색량 큰 순.
동시 4, 하루 24,000 (검색 API 한도 25,000/일), 500개마다 저장, 이어하기 있음.
429 를 만나면 깨끗하게 멈추고 저장한다.

모의 서버로 적중 탐지·저장·이어하기 셋 다 확인했다.

### 상품수가 들어오면 바뀌는 것
1. 경쟁강도를 추정치가 아니라 실측으로 바꾼다
2. 상품수 0~수십인 키워드 = 아직 아무도 안 파는 자리
3. 레시피·효능 같은 정보성 키워드가 상품수로 자연히 걸러진다
   (지금은 낱말 규칙으로만 거른다 → 황금키워드가 정보성으로 기우는 원인)

### 18단계 1차 실행 결과 (2026-09-14)

```
API HUB  /search/v1/shop  외 9개        → 전부 404 errorCode 300
openapi.naver.com /v1/search/shop.json  → 401 NID AUTH Result Invalid (1000)
openapi.naver.com /v1/search/shop       → 404
```

**401 은 빈손이 아니다.** 대조군(없는 경로)은 404 를 준다. 401 을 준다는 건
라우트가 실제로 존재하고 인증에서만 막혔다는 뜻이다. `.json` 이 붙은 쪽만
401 이고 안 붙은 쪽은 404 라는 것도 같은 얘기 — 정확히 그 주소가 맞다.

원인: 이 계정의 키는 NCP API HUB 키다. 검색 API 는 개발자센터
(developers.naver.com) 애플리케이션 키를 따로 쓴다. API HUB 쪽 404 는
이 계정이 검색 API 를 구독하지 않아 라우트가 안 뚫린 것으로 보인다
(구독 안 된 라우트는 210 을 준다고 봤었는데, 검색 API 는 아예 404 — 확인 필요).

조치: 키를 두 쌍으로 나눴다.
- `ID` / `SECRET` — API HUB (추세 · 쇼핑인사이트)
- `SEARCH_ID` / `SEARCH_SECRET` — 개발자센터 검색 API (상품수)

`loadKeys()` 별칭에 추가했고 `safe()` 도 새 키를 가린다.
18단계는 검색 키가 있으면 그걸 쓰고, 없으면 허브 키로 찔러본 뒤
401 이 나오면 발급 절차를 화면에 띄운다. 19단계는 18단계가 적어둔
`auth: "ncp" | "dev"` 를 그대로 따라 쓰고, 401/403 이면 즉시 멈춘다
(2만 번을 헛돌면 안 된다).

한도는 별개다. 검색 API 25,000/일 · API HUB 30,000/월.
상품수를 받아도 추세·쇼핑인사이트 한도를 깎지 않는다.

모의 서버로 네 가지 상태를 다 확인했다.
검색키 없음→401 진단 / 검색키 있음→적중 / 수집기 검색키 없음→차단 / 있음→수집.
