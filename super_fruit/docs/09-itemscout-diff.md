# 아이템스카우트와 우리 수치 대조

2026-09-14 · 사용자가 올린 아이템스카우트 "고구마 연관키워드" PDF(49개) 기준

## 1. 검색수 — 문제 없다

같은 키워드 29개를 맞대어 보았다.

| 키워드 | 아이템스카우트 | 우리 | 차이 |
|---|---|---|---|
| 김의준고구마 | 13,110 | 12,870 | -2% |
| 해남고구마 | 5,890 | 5,530 | -6% |
| 토울고구마 | 4,040 | 3,980 | -1% |
| 해들녘고구마 | 1,360 | 1,360 | 0% |
| 강화도고구마 | 710 | 710 | 0% |

**29개 중 27개가 오차 10% 이내, 차이 중앙값 0.0%.**
남은 차이는 수집 날짜가 달라서다. 둘 다 같은 네이버 검색광고 API 를 쓴다.

## 2. 경쟁강도 — 아예 다른 지표다

PDF 에서 공식을 역산했다.

```
경쟁강도 = 상품수 ÷ 검색수
```

48개 전부 이 식과 일치했다(100%).

| 키워드 | 상품수 | 검색수 | 계산 | 표기 |
|---|---|---|---|---|
| 김의준고구마 | 386 | 13,110 | 0.029 | 0.03 |
| 해남고구마 | 5,061 | 5,890 | 0.859 | 0.86 |
| 토울고구마 | 741 | 4,040 | 0.183 | 0.18 |

우리 경쟁강도는 전혀 다른 것이다.

```
우리 = 0.55 × (광고깊이/15) + 0.45 × (1위입찰가/2500),  0~10 으로 환산
```

**상품수 원본이 없어서 만든 대용품이다.** 쇼핑검색 API 가 2026-07-31 종료됐다.
값의 크기도 뜻도 다르므로 아이템스카우트 수치와 나란히 놓고 비교하면 안 된다.

## 3. 의도 분류 — 우리 분류는 맞았다

아이템스카우트가 쇼핑성이라 한 29개를 우리도 **29개 전부 쇼핑성**으로 봤다.
우리 고구마 키워드 412개 중 402개가 쇼핑성이다.

"정보성처럼 보인다"는 인상의 실제 원인은 분류가 아니라 **정렬**이다.
검색량 순으로 세우면 요리 키워드가 위로 온다.

```
고구마줄기볶음 116,440   고구마줄기김치 55,300   고구마순김치 45,590
고구마순볶음 35,050      고구마맛탕 14,140      고구마에어프라이어 14,530
```

아이템스카우트 목록에는 이것들이 없다. 그쪽은 **대표카테고리:고구마** 로 걸렀기 때문이다.
대표카테고리는 그 키워드로 실제로 팔리는 상품의 카테고리이고, 쇼핑 검색 결과를 봐야 안다.
우리는 그 데이터가 없어 키워드 글자로만 묶는다. 그래서 요리 키워드가 같이 들어온다.

광고 신호로 가를 수 있는지도 재보았다. 안 된다.

```
아이템스카우트 쇼핑성 29개   광고깊이 7.03 · 1위입찰가 2,325원 · 입찰가있음 100%
요리 어미 968개              광고깊이 6.08 · 1위입찰가 1,236원 · 입찰가있음  91%
```

고구마줄기볶음도 광고깊이 7 에 입찰가 400원이다. 광고주가 레시피 키워드에도 붙는다.

## 4. 그래서 막힌 곳은 하나다 — 상품수

상품수만 있으면 세 가지가 한 번에 풀린다.

1. 경쟁강도를 아이템스카우트와 같은 식으로 계산
2. 대표카테고리 추정 (상품이 몰린 카테고리)
3. 요리 키워드 걸러내기 (상품수가 검색수에 비해 터무니없이 적은 것)

쇼핑검색 API 가 종료됐지만 API HUB 로 이관됐을 가능성이 남아 있다.
검색어트렌드가 `/search-trend/v1/search`, 쇼핑인사이트가 `/shopping/v1/...` 로 살아 있었다.
쇼핑검색도 같은 게이트웨이에 있는지 확인해야 한다. → 확인 필요

## 상품수 확보 시도 (2026-09-14)

경쟁강도 = 상품수 ÷ 한달 검색수. 48/48 키워드로 아이템스카우트와 대조해
식을 확정했다. 검색수는 우리가 이미 갖고 있으니 남은 건 상품수 하나다.

### 18단계 — 자리 찾기 (`fetch-hub.mjs --shop-count`)
없는 경로가 뭘 돌려주는지 대조군으로 먼저 재고, 그것과 다른 응답만 본다.
두 호스트에 12개 후보를 시험 키워드 하나로 훑는다.

- API HUB (`naverapihub.apigw.ntruss.com`, NCP 헤더)
  `/search/v1/shop` · `/search/v1/shop.json` · `/search/v1/shopping` ·
  `/shopping/v1/search` · `/shop/v1/search` · `/shopping-search/v1/search` ·
  `/shopping/v1/shop` · `/search-shop/v1/search` · `/commerce/v1/search` ·
  `/v1/search/shop.json`
- 옛 개발자센터 (`openapi.naver.com`, X-Naver-Client-Id/Secret)
  `/v1/search/shop.json` · `/v1/search/shop`

이관 규칙이 `/v1/search/news.json` → `/search/v1/news` 였으니
`/search/v1/shop` 이 제일 유력하다. 응답에 `total`/`totalCount`/`result.total`
중 하나라도 있으면 적중으로 보고 `naver-out/hub-shopcount.json` 에 적는다.

주의: 이 세션의 키는 NCP API HUB 키다. 옛 주소 쪽이 200을 주려면
developers.naver.com 애플리케이션 키가 따로 있어야 한다.

### 19단계 — 전부 채우기 (`--shop-count-all`)
주소를 `hub-shopcount.json` 에서 읽는다. 목표 목록은 16b 가 떨구는
`naver-out/section-keywords.txt` — 화면이 실제로 쓰는 키워드만, 검색량 큰 순.
동시 4, 하루 24,000 (검색 API 한도 25,000/일), 500개마다 저장, 이어하기 있음.
429 를 만나면 깨끗하게 멈추고 저장한다.

모의 서버로 적중 탐지·저장·이어하기 셋 다 확인했다.

### 상품수가 들어오면 바뀌는 것
1. 경쟁강도를 추정치가 아니라 실측으로 바꾼다
2. 상품수 0~수십인 키워드 = 아직 아무도 안 파는 자리
3. 레시피·효능 같은 정보성 키워드가 상품수로 자연히 걸러진다
   (지금은 낱말 규칙으로만 거른다 → 황금키워드가 정보성으로 기우는 원인)

### 18단계 1차 실행 결과 (2026-09-14)

```
API HUB  /search/v1/shop  외 9개        → 전부 404 errorCode 300
openapi.naver.com /v1/search/shop.json  → 401 NID AUTH Result Invalid (1000)
openapi.naver.com /v1/search/shop       → 404
```

**401 은 빈손이 아니다.** 대조군(없는 경로)은 404 를 준다. 401 을 준다는 건
라우트가 실제로 존재하고 인증에서만 막혔다는 뜻이다. `.json` 이 붙은 쪽만
401 이고 안 붙은 쪽은 404 라는 것도 같은 얘기 — 정확히 그 주소가 맞다.

원인: 이 계정의 키는 NCP API HUB 키다. 검색 API 는 개발자센터
(developers.naver.com) 애플리케이션 키를 따로 쓴다. API HUB 쪽 404 는
이 계정이 검색 API 를 구독하지 않아 라우트가 안 뚫린 것으로 보인다
(구독 안 된 라우트는 210 을 준다고 봤었는데, 검색 API 는 아예 404 — 확인 필요).

조치: 키를 두 쌍으로 나눴다.
- `ID` / `SECRET` — API HUB (추세 · 쇼핑인사이트)
- `SEARCH_ID` / `SEARCH_SECRET` — 개발자센터 검색 API (상품수)

`loadKeys()` 별칭에 추가했고 `safe()` 도 새 키를 가린다.
18단계는 검색 키가 있으면 그걸 쓰고, 없으면 허브 키로 찔러본 뒤
401 이 나오면 발급 절차를 화면에 띄운다. 19단계는 18단계가 적어둔
`auth: "ncp" | "dev"` 를 그대로 따라 쓰고, 401/403 이면 즉시 멈춘다
(2만 번을 헛돌면 안 된다).

한도는 별개다. 검색 API 25,000/일 · API HUB 30,000/월.
상품수를 받아도 추세·쇼핑인사이트 한도를 깎지 않는다.

모의 서버로 네 가지 상태를 다 확인했다.
검색키 없음→401 진단 / 검색키 있음→적중 / 수집기 검색키 없음→차단 / 있음→수집.

### 개발자센터 경로는 막혔다 (2026-09-14)

401 을 보고 developers.naver.com 에서 검색 API 키를 받으라고 안내했는데,
애플리케이션 등록 화면의 "사용 API" 목록에 **검색이 아예 없다.**
(네이버 로그인 · 인증서 · 전자문서 · 네이버페이 배송지 · 카페 · 캘린더 · 캡차 …)

검색하니 여러 기사가 같은 얘기를 한다: 쇼핑 · 책 · 전문자료 검색 API 는
**2026-07-31 종료**, 블로그 · 뉴스 · 카페 검색과 검색어트렌드 · 쇼핑인사이트만
API HUB 로 이관. 기존 키는 2027-06-30 까지 유효.

그러면 401 은 "인증 게이트는 아직 서 있는데 뒤에 서비스가 없다"로 읽힌다.

**아직 확정은 아니다.** HUB 의 404 가 "그런 API 없음"인지 "이 계정 미구독"인지
구분이 안 됐다. 그래서 18단계에 결정적 대조군을 넣었다.

```
/search/v1/blog 와 /search/v1/news 를 우리 키로 먼저 부른다
  살아있는데 쇼핑만 404 → 쇼핑 API 는 진짜 없어졌다 (공식 경로 끝)
  똑같이 404          → 404 는 미구독이라는 뜻. NCP 콘솔에서 신청하면 된다
```

모의 서버로 두 판정 다 확인했다.

### 상품수 대체 지표를 찾아봤지만 없다

검색광고 API 가 주는 것으로 상품수를 대신할 수 있는지 34,107개로 재봤다.

**가설 1 — 광고가 붙는가로 정보성을 거른다: 실패.**
```
광고노출수(depth)>0  32,540 / 34,107 = 95.4%
정보성이라 확신한 키워드 7개 중 7개에 광고가 붙어 있다 (오탐 100%)
고구마효능 광고 5개 · 단호박효능 7개 · 토마토효능 10개
```
효능·칼로리 키워드에도 광고주가 다 붙는다. 판별력이 없다.

**가설 2 — 입찰가 수준으로 가른다: 실패.**
```
정보성(효능·칼로리·만드는법…)  977개  입찰가 중앙값   920원  CTR 1.05%
쇼핑성(선물세트·N kg·산지직송…) 2,019개 입찰가 중앙값 1,230원  CTR 2.02%

입찰가 1.3배 차이. 문턱을 어디에 둬도 오탐이 같이 따라온다.
  500원↑  쇼핑성 90% 잡고 정보성 79% 오탐
 1000원↑  쇼핑성 59% 잡고 정보성 45% 오탐
 2000원↑  쇼핑성 25% 잡고 정보성 17% 오탐
```

CTR 만 2배 차이가 나는데, 2배로는 못 가른다.

결론: **검색광고 API 안에 상품수를 대신할 것은 없다.** 경쟁강도는
상품수가 있어야만 나온다. 억지로 만들면 틀린 숫자를 파는 사람에게
보여주게 된다. 그건 안 한다.

### 판정: 쇼핑 검색 API 는 실제로 없어졌다 (2026-09-14, 2차 실행)

```
/search/v1/blog   401  "요청한 API는 이 Application에서 활성화되어 있지 않습니다"
/search/v1/news   401  같음
/search/v1/shop   404  "Not Found Exception · URL not found."
```

같은 호스트, 같은 키, 같은 경로 모양(`/search/v1/<종류>`). 종류 이름만 다르다.

- blog · news → **게이트웨이가 그 경로를 안다.** 다만 이 Application 에서 안 켜져 있다.
- shop → **게이트웨이가 그런 경로를 모른다.**

미구독이었다면 shop 도 401 이 나왔어야 한다. 404 가 나왔다.
기사 내용(2026-07-31 종료)이 우리 계정에서 직접 확인됐다.

남은 확인 한 가지: NCP 콘솔 > API HUB > Application 설정의 API 목록에
쇼핑 검색이 아예 없는지. 콘솔이 최종 권위다. 우리 탐침은 "라우트 없음"까지만 말한다.

**버그 하나 고쳤다.** 판정 분기 순서가 틀려서, 기준점이 살아있는데도
`!hasDev && sawAuthFail` 가지가 먼저 걸려 "developers.naver.com 가서
키 받아라" 를 화면에 찍었다. 이미 막힌 길로 안내한 것이다.
liveOk 판정을 맨 앞으로 올렸다.

### 광고 데이터로 경쟁강도를 대신할 수 있나 — 없다

```
월평균노출광고수(depth) 분포          입찰가 1위 ÷ 3위
   0개   4.6%                       중앙값 1.76배
   3개  21.3%  ←                    1.3배 미만(만석) 20%
   7개  21.9%  ←                    2배 이상(위가 빔) 42%
   8개  22.9%  ←
  10개  13.3%
```

3 · 7 · 8 에 66% 가 몰려 있다. 자연스러운 분포가 아니라 네이버가
구간으로 뭉개서 주는 값이다. 거친 신호다.

그리고 결정적으로, "광고 안 찬 자리" 를 검색량 순으로 뽑으면
**고구마줄기볶음 · 무화과효능** 같은 정보성 키워드가 그대로 올라온다.
광고 데이터는 황금키워드가 정보성으로 기우는 문제를 하나도 못 푼다.

→ 경쟁강도는 만들지 않는다. 억지로 만든 숫자를 파는 사람 화면에 박지 않는다.

### 그러면 정보성 문제는 무엇으로 푸는가 — 쇼핑인사이트

이미 되는 것이고 공식이다. 쇼핑인사이트 카테고리 키워드에 잡힌다는 건
정의상 **네이버쇼핑 안에서 검색된 키워드**라는 뜻이다. 낱말 규칙보다 훨씬 강하다.

지금 커버리지 6.7%. 10월 1일 한도가 풀리면 566k 전체가 아니라
화면이 쓰는 42k 섹션 키워드를 겨냥해 모은다. 순서만 바꾸면 된다.

**상품수는 공식 경로로 못 구한다. 확정.** 경쟁강도는 만들지 않는다.

### 정보성 판별 — 네 번 재고 네 번 실패했다

| 광고가 붙는가 | 정보성 7/7 에도 붙음. 전체 95.4% 가 광고 있음 | 오탐 100% |
| 입찰가 수준 | 정보성 920원 · 쇼핑성 1,230원 | 1.3배. 못 씀 |
| 쇼핑인사이트에 잡히는가 | 날것 25.7% 대 6.4% 인데 **검색량 편향이었다**. 같은 구간에서 재면 90% 대 100% | 차이 없음 |
| 쇼핑클릭지수 ÷ 검색량 | 중앙값 0.189 대 0.441 (2.3배) 인데 **방향이 뒤집힌다** | 못 씀 |

마지막 것이 제일 그럴듯해 보여서 문턱까지 세워봤는데, 실제 값을 보면
정규화가 만든 허상이었다.

```
쇼핑성 낮은 쪽   추석선물세트 0.007 · 쌀10KG 0.017 · 한우선물세트 0.023
정보성 높은 쪽   콜라비효능 1.150 · 레몬밤효능 1.119 · 자색양파즙효능 1.092
```

검색량이 큰 키워드일수록 비율이 작아진다. 의도가 아니라 분모를 잰 것이다.

### 다섯 번째 가설 — 지식iN 문서수 (20단계)

"콜라비효능" 은 사람들이 **묻는 말**이고 "한우선물세트" 는 묻는 말이 아니다.
지식iN 문서수가 그 차이를 잡아줄 것이라는 가설.

앞의 네 개와 달리 방향이 분명하고, 콘솔 목록에 있어서 체크 한 번이면 켜진다.
같은 키를 그대로 쓴다(401 메시지가 "이 Application에서 활성화되어 있지
않습니다" 였으니 Application 수정으로 켜진다).

**가설일 뿐이다.** 네 번 틀렸으니 42,000번 붓기 전에 80개로 먼저 잰다.
`--intent-test --api kin` · 80 호출 · 1분. 화면이 스스로 판정한다.
60%p 이상이면 전체 수집, 40~60%p 면 보조 지표, 40%p 미만이면 버린다.

모의 서버로 미활성(401 안내)과 활성(판정 출력) 둘 다 확인했다.
모의 서버 숫자는 내가 만든 것이라 의미가 없다. 실제 값은 실행해봐야 안다.

### 내보내기를 몇 번 해야 하나 (2026-09-14)

"키워드마다 연관키워드가 무수한데 그걸 일일이 다 넣자는 거냐" — 정당한 반문이라 쟀다.

화면 키워드 34,107개는 **734개 품목 묶음**으로 접힌다. 낱개가 아니다.

```
상위  10개 품목 →  6,560개  19.2%
상위  20개 품목 → 10,311개  30.2%
상위  30개 품목 → 12,814개  37.6%
상위  50개 품목 → 16,491개  48.4%
상위  80개 품목 → 20,495개  60.1%
상위 200개 품목 → 27,453개  80.5%
```

한 품목이 수백 개를 물고 있다. 선물세트 1,180 · 한우 900 · 과일 883 ·
갈비 831 · 사과 602 · 고구마 412.

**다만 확인 안 된 게 있다.** 아이템스카우트 내보내기 한 번이 몇 행을 주는지 모른다.
상한이 100행이면 고구마 412개가 한 번에 오지 않는다. 겹치는 비율도 모른다.
파일 하나를 실제로 받아봐야 안다. 그 전까지 커버리지를 약속하지 않는다.

그래서 importer 가 넣은 뒤 **화면 대비 몇 %가 채워졌는지**를 직접 찍게 했다.
행 수가 아니라 겹친 수를 본다. 2% 미만이면 경고도 띄운다.

**그리고 애초에 34,107개가 다 필요하지 않다.** 실제로 파는 품목은 20~30개다.
발굴은 우리 데이터(검색수·입찰가·추세·마진 — 전부 완전하다)로 하고,
후보가 좁혀졌을 때 그 품목만 경쟁강도를 채우면 된다.

## 연관 키워드 — 자료는 있었고 화면이 안 썼다 (2026-09-14)

보갬: "아리수사과를 검색하면 연관키워드가 나와야 하는데 피땅콩가격 ·
가시오이10KG · 히비키위스키가격 같은 게 가득하다."

맞는 지적이고 원인은 단순했다. 목록이 **전역 황금키워드 순위**였다.
검색은 히어로 카드만 바꾸고 목록을 좁히지 않았다.

그런데 연관 자료는 **이미 갖고 있었다.** 검색광고 `/keywordstool` 은 씨앗 하나를
주면 그 씨앗의 연관키워드를 돌려준다. 아이템스카우트 연관키워드 탭과 같은 출처다.
우리는 그 응답을 `hint` 로 적어두고 화면에서 안 쓰고 있었다.

**같은 hint 를 공유 = 같은 응답에서 나옴 = 서로 연관키워드.**

대조 결과 (아리수사과, hint 묶음 328개 vs 아이템스카우트 132개):
```
우리 상위 25 중 22개가 아이템스카우트 목록과 일치
안 겹치는 것은 대부분 띄어쓰기 변형 — 홍로 사과 · 아리수 사과 · 시나노 골드사과
(저쪽은 띄어쓰기를 다른 키워드로 센다. 우리 원칙과 같다)
```

한 갈래만 보면 틀린다. 아리수사과는 자기가 씨앗일 때 3개뿐이고,
자기를 물고 온 씨앗(홍로사과)의 형제가 326개다. **둘을 합친다.**

이제 검색·품목 칩·행 클릭 모두 연관 보기로 들어가고, 배너에 씨앗과 개수가
찍히며 "전체 목록으로" 로 빠져나온다. 연관 보기에서는 의도·판정 필터를 걸지 않는다.

## 아이템스카우트 실파일로 검증 (2026-09-14)

아리수사과 연관키워드 132행 엑셀을 받았다. 열이 예상보다 많다.
```
키워드 · 중복횟수 · 대표 카테고리 · 키워드 분류 · 쇼핑성 지수 · 정보성 지수
PC/모바일 광고단가 · PC/모바일 검색 · 총 검색수 · 상품수 · 경쟁강도
평균 클릭수 · PC/모바일 클릭률 · 클릭 경쟁률 · 클릭대비 광고비
```

### 우리 검색수는 맞다
70개 대조. **차이 중앙값 −2.5%**, ±20% 안에 83%. 수집 시점 차이로 설명되는 범위다.
큰 차이는 사과10KG(+103%) 처럼 검색량 자체가 작아 흔들리는 것들이다.

### 분류 규칙의 결함을 하나 잡았다
아이템스카우트 분류와 69/70 일치했는데, 틀린 하나가 **세척사과**였다.
`RE_HOWTO` 에 `세척`·`손질`·`보관`·`숙성`이 낱말째로 들어 있어서
손질오징어 · 보관용기 · 숙성한우까지 정보성이 될 뻔했다.
`(법|방법)$` 가 이미 세척법 · 보관방법을 잡으므로 낱말째 항목을 뺐다.
18개 표본으로 확인 후 교체 → **70/70 (100%) 일치.**

### 가져오기가 더 많은 것을 챙긴다
`import-itemscout.mjs` 가 상품수 · 경쟁강도에 더해 **대표 카테고리 · 키워드 분류 ·
쇼핑성 지수**까지 읽는다. 팩커가 `prod · icomp · icat` 세 열로 싣는다.
경쟁강도는 저쪽이 적어준 값을 그대로 쓴다(우리 검색수로 나누면 2.5% 어긋난다).

화면 표에 **상품수 · 경쟁강도** 칸을 새로 넣었다. 없으면 `—` 로 비워둔다.
실파일을 심고 브라우저로 13/13 완전 일치를 확인했다.
```
홍로사과  54,726 / 0.92   아리수사과 2,598 / 0.07   사과선물세트 74,488 / 9.22
```
