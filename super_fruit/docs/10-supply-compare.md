# 공급가 비교 — 설계와 근거

2026-09-16. 보갬: "각 공급사별 사이트에서 공급가를 엑셀이나 open API 로 공개해준다.
문제는 표현 방식이 다르다는 것. 어떤 곳은 2kg/6과를 대과라 하고 어떤 곳은
2kg/8과를 대과라 한다. **핵심은 '대과' 라는 단어보다 숫자에 착안하는 것.**"

그 말이 이 기능의 설계 전체다.

## 먼저 바로잡을 것

"원래 있던 공급가 비교 섹션이 사라졌다" — 사라진 게 아니라 **만든 적이 없다.**
`docs/05-weapon-spec.md` 의 기획에만 있었고 `README.md` 에 `미착수` 로 적혀 있었다.
이번이 처음 구현이다.

## 두 숫자만 본다

```
g/과  = 중량 ÷ 과수      진짜 크기
원/kg = 공급가 ÷ 중량    진짜 단가
```

등급 낱말은 버리지 않고 옆에 적어둔다. 참고는 되지만 판정에는 안 쓴다.
낱말과 실측이 어긋나면 배지를 붙인다.

실제 시험 결과. 같은 홍옥 2kg인데:
```
A사  7,950원/kg  250 g/과   "특대" 라고 부름   ← 제일 비싼데 제일 작다
B사  5,200원/kg  385 g/과   "중"  이라고 부름   ← 제일 크다
```

## 크기대를 우리가 다시 매긴다

품목마다 과실 크기가 다르므로 절대 그램 수를 박아두지 않는다.
**그 품목에 실제로 나온 매물들의 g/과 분포를 사분위로 잘라** 특대·대·중·소를 매긴다.
공급사가 뭐라 부르든 상관없고, 시장에 나온 물건이 바뀌면 기준도 따라 움직인다.

## 같은 규격끼리만 본다

2kg 과 10kg 을 한 표에 섞었더니 마진 −117% 가 나왔다.
10kg 공급가를 2kg 판매가에 견준 값이다. 숫자는 맞지만 뜻이 없다.
중량 칩으로 한 번에 한 규격만 본다. 기본값은 그 품목에 제일 많은 규격.
원/kg 은 규격을 가로질러 비교되므로 그대로 둔다.

## 품종 사전 2,782개

공급사는 "홍옥", 우리 키워드 사전에는 "홍옥사과" 만 있었다. 안 맞았다.
나주배도 마찬가지다. 산지가 앞에 붙으면 빠진다.

세 갈래로 모았다 (`build-varieties.mjs` → `varieties.json`).
1. `supply-calendar.json` 의 202품종 45카테고리 — 품종 → 기준품목
   품목 이름을 뗀 단독형도 등록한다 (홍로사과 → 홍로)
2. 산지 52곳 × 기준품목 조합 — 나주배 → 배
3. 달력에 없는 흔한 품종 손으로 보탬 — 홍옥 · 아리수 · 후지 · 베니하루카

여러 개가 걸리면 긴 것이 이기고, 길이가 같으면 품종이 기준품목을 이긴다.
(홍옥·사과 둘 다 두 글자여서 사과가 먼저 잡히던 버그를 이걸로 고쳤다)

## 열 이름을 맞출 필요가 없다

공급사마다 엑셀 모양이 다르다. 이름으로 찾고, 머리글이 아예 없으면 내용으로 짚는다.
- 글자가 길고 숫자가 아닌 열 → 상품명
- 값이 크고 거의 전부 숫자인 열 → 가격 (500 ~ 5,000,000 범위)

머리글은 첫 줄이 아닐 수 있어 25줄까지 훑는다. 시트가 여럿이면 행이 제일 많은 것을 쓴다
(1번 시트가 안내문인 경우가 흔하다).

세 가지 모양으로 시험했고 전부 통과했다.
```
표준 CSV, 머리글 1행                     5행 → 5건
머리글 4행, 열 이름 다름                  5행 → 5건
xlsx, 머리글도 열 이름도 없음             6행 → 6건   ← 내용으로 추정
합계 16건 · 품목 100% · 중량 100% · 과수 81%
```

## 잡은 버그

- **등급 낱말 순서.** `중대과` 가 `대` 로 잡혔다. 정규식 배열 순서가 곧 우선순위라
  긴 낱말을 앞으로 올렸다. 특대 → 중대 → 대 → 중 → 소
- **경고 배지가 반대로.** `normGrade()` 가 돌려준 숫자를 `BANDS.indexOf()` 에
  다시 넣어서 늘 −1 이 나왔다. "중" 이라 부른 것이 실제로는 특대인 줄에도
  "부른 값보다 작음" 이 붙었다. 이제 양쪽 다 지수로 비교하고,
  큰 쪽이면 초록 배지를 붙인다.
- **청소 찌꺼기.** 낱말만 잘라내서 "업소용" 에서 "용" 이 남았다. 정규식으로 통째로 지운다.

## 흐름

```
공급사 엑셀 → supply 폴더 → 22단계 → naver-out/supply.json
            → 16b (pack/supply.js) → build-web (data-supply.js) → 화면
```

공급가 파일이 없으면 탭에 안내문만 나온다. 다른 탭에 영향 없다.
브라우저로 있을 때·없을 때 둘 다 확인했다. JS 오류 0.

## 아직 안 된 것

- **open API 연동.** 지금은 파일만 읽는다. 공급사가 API 를 주면 그때 붙인다.
- **사전에 없는 품종.** 못 찾은 상품명을 화면에 찍어준다. 보고 보태면 된다.
- **과수 없는 매물.** 중량만 있으면 원/kg 은 나오지만 g/과 는 못 낸다.
  시험에서 19% 가 그랬다. 크기 비교에서만 빠지고 단가 비교에는 들어간다.

## 실제 공급사 자료로 검증 (2026-09-16)

온그린 · B사 · C사가 **같은 태추단감**을 파는 화면 세 장을 받았다.
표기 방식이 셋 다 다르다.

```
온그린  태추단감(소과/35과내외)-5kg        22,500원
B사    태추단감 1kg 소과(5과내외)          7,300원
C사    중소 1.5kg 8-10과                14,800원      ← 품목명이 옵션에 없다
```

**16건 전부 읽었다. 실패 0.** 중량 100% · 과수 100%.

### 가설이 실제 자료로 증명됐다

```
온그린 "소과"  =  143 g/과
B사   "소과"  =  200 g/과
                40% 차이
```

그리고 1kg 짜리를 나란히 놓으면:
```
B사    7,300원/kg   200 g/과   "소과"
온그린  7,800원/kg   143 g/과   "소과"   ← 더 비싸고 더 작다
```
낱말만 봤으면 둘을 같은 물건으로 알고 비싼 쪽을 샀을 것이다.

### 비교 열쇠를 품목에서 품종으로 바꿨다

달력이 태추단감 · 청도반시 · 대봉감을 모두 `감` 카테고리에 넣어둔다.
파는 사람에게 그 셋은 다른 물건이다. `key = 품종 || 품목` 을 새로 두고
화면이 그것으로 묶는다. 홍옥과 부사를 "사과" 로 뭉개던 문제도 같이 풀렸다.

### 경고 배지의 기준을 두 번 고쳤다

**1차 — 우리 사분위 등급과 낱말을 비교.** 거의 모든 줄에 배지가 붙었다.
우리 등급은 매물들 사이의 상대값이라 낱말과 어긋나는 게 정상이다. 뜻이 없었다.

**2차 — 다른 공급사가 같은 낱말로 파는 것과 비교.** 방향은 맞는데
온그린이 소과 다섯 줄을 올려서 143g 이 "시장 소과" 가 돼버렸다.
줄 수로 세면 SKU 를 많이 올린 곳이 기준을 독점한다.

**3차 — 공급사마다 먼저 하나로 접고 그 다음 중앙값.** 이제 맞다.
```
온그린 소과 143g → "다른 곳 소보다 29% 작다"   ← 이 줄에만 붙는다
```

### 화면 구성 — 원본과 계산을 나란히

보갬: "실제 업체가 제공해주는 기본 옵션&공급가를 기본적으로 표기하면서
너가 제안해준 진짜 크기, 진짜 단가를 같이 병행해서 표기"

표를 세 덩어리로 나눴다.
```
공급사 │ 공급사가 준 그대로      │ 우리가 잰 값              │ 이 공급가로 팔면
       │ 옵션명·공급가 · 부른등급 │ 중량 · 과수 · g/과 · 원/kg │ 마진 · 마진율
```
공급사 문자열은 자르거나 고치지 않고 그대로 싣는다.

## open API 연동 (23단계)

20곳이 넘는다고 한다. 응답 모양이 제각각일 것이므로 **구조를 스스로 훑는 길**을 먼저 냈다.

```
node fetch-supply.mjs --probe
```

한 번씩만 불러서 (1) 상품 배열이 어디 있는지 (2) 열 이름이 뭔지
(3) 우리 이름과 어떻게 짝지을지를 찍는다. 저장은 안 한다.

모의 API 세 종류로 시험했다.
```
data.items 중첩 + 쪽번호      → 열 이름 그대로 짚음
맨 위가 배열 + 로마자 열 이름   → goods_nm · danga 를 짚음
result.list.rows 3단 중첩     → 배열 위치 스스로 찾음
401 인증 실패                 → 오류만 찍고 넘어감
```

처음엔 `goods_nm` · `danga` 를 못 짚어 한 곳을 통째로 놓쳤다.
국내 공급사가 쓰는 로마자 열 이름을 사전에 보탰다.

못 짚으면 **열 이름을 화면에 찍어준다.** 그걸 보내주면 `map` 을 채워 돌려준다.

`suppliers.json` 은 키를 담으므로 압축본에 넣지 않는다 (`-x suppliers.json`).
`.gitignore` 에도 넣었다.
