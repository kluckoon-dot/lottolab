## 1. 확인된 사실

### 제공 API — 세 갈래

| 묶음 | 포함 기능 (기능 맵 기준) |
|---|---|
| **Search API** | Local · Web · Image · Cafe · Knowledge iN · Adult Filter · **Type Correction** |
| **Trend** | **Search Trend** · **Device** · **Period** · User Interest · Keyword Flow · **Type Correction** |
| **Shopping** | **Shopping Insight** · **Keyword Insight** · **Category Trend** · **Customer Segment** · Commerce Demand |
| Operations | Console · Application · Billing · Monitoring · Data Source (운영 기능) |

우측 제품 목록은 **검색어 트렌드 · 쇼핑 인사이트 · 검색 API** 셋이다.
기능 맵의 이름은 마케팅 표기이므로 실제 엔드포인트 이름과 1:1이라고 단정하지 않는다. → 확인 필요

### 요금 — 전부 0원, 단 구간이 있다

| API | 구간 | 호출량 | 요금 | 비고 |
|---|---|---|---|---|
| 검색어 트렌드 | 무료 | 0 ~ 30,000건 | 0원 | 기본 무료 |
| 검색어 트렌드 | 유료 | 30,001 ~ 50,000건 | 0원 | **한시적** 무료 |
| 쇼핑 인사이트 | 무료 | 0 ~ 30,000건 | 0원 | 기본 무료 |
| 쇼핑 인사이트 | 유료 | 30,001 ~ 50,000건 | 0원 | **한시적** 무료 |
| 검색 API | 무료 | 0 ~ 775,000건 | 0원 | 일 최대 25,000건 |

VAT 별도.

### 구간 단위는 '월'로 읽힌다

검색 API 행에 단서가 있다.

```
775,000 ÷ 25,000 = 31
```

**일 한도 25,000건 × 31일 = 775,000건.** 구간이 월 단위라는 뜻이다.
따라서 검색어트렌드와 쇼핑인사이트도 **월 30,000건**으로 본다.
다만 이 둘의 일 한도는 표에 없다. → **확인 필요**

### 30,001 ~ 50,000 구간을 계획에 넣지 마라

"한시적 무료"다. 지금은 0원이지만 유료로 바뀐다.
**30,000건을 지속 가능한 숫자로 잡고, 20,000건은 덤으로 취급한다.**

## 2. 우리 규모와 맞춰보기

### 키워드 수 추정

202품종을 `/keywordstool`에 넣으면 품종당 연관 키워드가 딸려 온다.
정확한 배율은 **40품종 수집이 끝나면 실측된다.** 그 전까지는 추정이다.

```
품종당 평균 연관 키워드 100개 가정 → 중복 제거 후 1만 ~ 2만 개
```

아래 계산은 **15,000개** 기준이다. 실측 후 다시 계산한다.

### 검색어 트렌드 — 여유 있다

검색어트렌드는 한 번 호출에 **키워드 그룹을 여러 개** 넣을 수 있다(문서상 5개). → 확인 필요

```
15,000 키워드 ÷ 5 = 3,000 호출
3,000 / 30,000 = 월 예산의 10%
```

게다가 **3년 주간 추세는 한 번 받으면 156주가 통째로 온다.**
매일 다시 받을 이유가 없다. 주 1회 갱신이면 충분하고, 그러면 월 12,000 호출.
**월 30,000 안에서 충분히 돈다.**

### 쇼핑 인사이트 — 여기가 병목이다

연령 · 성별 · 기기는 각각 다른 호출이다.

```
15,000 키워드 × 3종 = 45,000 호출
45,000 > 30,000        ← 한 달에 한 바퀴를 못 돈다
```

**한 번에 여러 키워드를 받아주는지가 관건이다.** 받아준다면 문제가 사라진다. → 확인 필요

### 검색 API — 775,000건이 거의 놀고 있다

우리가 쓸 일이 없어 보이지만, 쓸 데가 하나 있다.

쇼핑검색 API가 종료돼서 **상품수 원본이 없다**(`docs/01`, `docs/02`).
지금은 광고 깊이와 입찰가로 경쟁강도를 대신 재고 있는데,
**웹문서 · 블로그 검색 결과 총건수**를 콘텐츠 경쟁도 지표로 얹을 수 있다.

```
15,000 키워드 × 2종(웹, 블로그) = 30,000 호출
30,000 / 775,000 = 월 예산의 4%
```

상품 경쟁과 콘텐츠 경쟁은 다른 축이므로 상품수를 대체하지는 못한다.
**보조 지표로만 쓰고, 화면에 "콘텐츠 경쟁"이라고 따로 이름 붙인다.**

## 3. 원칙과 예산의 충돌, 그리고 해법

`docs/05-weapon-spec.md`의 원칙은 **키워드를 버리지 않는다**이다.
쇼핑인사이트 예산은 한 달에 한 바퀴를 못 돌 수 있다. 정면으로 부딪힌다.

**버리는 것과 늦게 받는 것은 다르다.**

| 하지 않는 것 | 하는 것 |
|---|---|
| 검색량 적다고 영구 제외 | 전부 큐에 넣고 **순환 수집** |
| 대표 키워드만 수집 | 우선순위만 다르게, 결국 전부 받음 |
| 오래된 값을 새 값인 척 표시 | **조회 시각을 화면에 그대로 표시** |

### 갱신 주기를 지표마다 다르게 잡는다

| 지표 | 출처 | 갱신 주기 | 이유 |
|---|---|---|---|
| 월 검색수 · 클릭 · CTR · 경쟁도 | 검색광고 | 주 1회 | 월 단위 통계라 자주 볼 이유 없음 |
| **1~3위 입찰가** | 검색광고 | **매일 2회** | 경쟁 입찰이라 매일 움직인다 |
| 3년 주간 추세 | 트렌드 | 주 1회 | 156주가 한 번에 온다 |
| 연령 · 성별 · 기기 | 쇼핑인사이트 | **순환** | 예산 병목. 인구 구성은 급변하지 않는다 |
| 도매 시세 | KAMIS | 매일 1회 | 매일 조사된다 |
| 공급가 | 공급사 | 매일 2회 | 발주에 직결 |

**인구 구성이 순환 대상이 되는 건 우연이 아니다.** 연령·성별 비중은 가장 느리게 변하는 값이다.
입찰가는 매일 바뀌고 연령 구성은 분기로 바뀐다. **예산을 빨리 변하는 쪽에 쓴다.**

### 순환 순서

```
1순위  시즌 진입 · 공급 중 품종의 키워드   (수확 캘린더가 공짜로 걸러준다)
2순위  판정이 린정 · 반린정인 키워드
3순위  나머지 전부                        (순환, 몇 주에 한 바퀴)
```

비시즌 품목에 예산을 쓰지 않는다. 그래도 **영구 제외는 없다.** 시즌이 오면 1순위가 된다.

## 4. 시작 전에 확인할 것

| 확인할 것 | 왜 중요한가 | 방법 |
|---|---|---|
| **호출 주소** | 이관하며 바뀜. 모르면 아무것도 못 함 | `4-check-hub.bat` |
| 인증 헤더 방식 | 두 가지 후보 | 같은 파일 |
| 검색어트렌드 1회 최대 키워드 그룹 수 | 예산이 5배 갈린다 | 실호출 |
| **쇼핑인사이트 연령/성별/기기의 묶음 조회 가능 여부** | **병목이 사라지느냐 마느냐** | 실호출 |
| 트렌드 · 인사이트의 일 한도 | 표에 없음 | 콘솔 또는 실호출 |
| Application 에 API 가 붙어 있는지 | 안 붙으면 키가 맞아도 403 | 콘솔 |
| 실제 키워드 총개수 | 위 계산의 전제 | **40품종 수집** |

## 5. Type Correction — 쓰되, 적용하지 않는다

Search API 와 Trend 양쪽에 **오타 교정(Type Correction)** 이 있다.

`docs/05`의 원칙상 **교정 결과로 키워드를 바꾸거나 합치면 안 된다.**
"샤인머스캣"과 "샤인머스켓"은 각각의 시장이다.

대신 **정보로는 값지다.**

```
샤인머스캣  →  네이버는 이것을 "샤인머스켓"으로 교정한다
```

이건 두 키워드가 **같은 상품을 가리킨다**는 신호다. 합치라는 뜻이 아니라
**"이 둘은 한 상품의 두 시장"이라고 화면에서 이어 보여주라**는 뜻이다.

- 저장은 `correctedTo` 필드에 따로
- 화면에는 "연결된 표기" 로 나란히 표시
- 판정 · 점수 · 입찰가는 **각자 따로** 계산
