# 아이템스카우트 + 판다랭크 결합 검토

2026-09-10 · 질문: "두 서비스의 장점을 모은 하나의 서비스, 가능한가?"

---

## 결론

**기능은 만들 수 있다. 근데 그 둘의 핵심 기능은 크롤링으로 굴러간다.**
**따라 하려면 크롤링을 해야 하고, 크롤링해서 파는 순간 판례가 정면으로 걸린다.**

정확한 판정은 용도에 따라 갈린다.

| 무엇을 | 판정 |
|---|:--:|
| 두 서비스 클론을 만들어 **판매** | **패스** |
| 같은 기능을 **내부 전용**으로 (크롤링 제외) | **반린정** |
| 수요 + **공급가**를 결합한 마진 툴, 내부 전용 | **린정** |

---

## 1. 두 서비스의 장점 분해

**아이템스카우트 — 정밀 지표와 추적**
- 키워드 지표·차트·등록 상품·연관 키워드를 한 화면에
- 네이버 쇼핑 **상품 노출 순위 추적**
- **판매량·매출액 추정치**, 리뷰 분석
- 카테고리별 랭킹, 아이템 발굴

**판다랭크 — 발굴과 판단**
- 기능 4축: 키워드 분석 / 상품 분석 / 상품 순위 / **키워드 찾기**
- 지표: 월 검색량, **6개월 시장규모**, 경쟁강도, 평균 광고 클릭비, **시즌성**, 로켓상품 비율
- 1등 상품이 뭔지, 저렴하게 소싱 가능한 관련 상품이 뭔지까지 제시
- 초보 셀러 친화적. **"그래서 뭐 팔아?"에 답을 준다**

**장점을 합치면** = 판다랭크의 *발굴·판단* + 아이템스카우트의 *정밀 지표·추적*

## 2. 그런데 기능마다 데이터 원천이 다르다

여기가 진짜 판정 지점이다. 기능 목록이 아니라 **원천**으로 봐야 한다.

| 기능 | 원천 | 지금 얻을 수 있나 |
|---|---|:--:|
| 월 검색수(PC/MO), 클릭수, CTR | 네이버 검색광고 API | **가능** |
| 평균 광고 클릭비, 예상 입찰가 | 네이버 검색광고 API | **가능** |
| 검색 추세, **시즌성** | 검색어트렌드 (API 허브) | **가능** |
| 카테고리 클릭 구성 (기기·성별·연령) | 쇼핑인사이트 (API 허브) | **가능** |
| 마진 계산기 | 자체 계산 | **가능** |
| **공급가 비교** | 온그린 등 공급사 API | **가능** |
| **도매 실거래 시세** | KAMIS | **가능** |
| 상품수, 경쟁강도 | 쇼핑**검색** API | **불가** — 종료. 크롤링뿐 |
| 상품 노출 순위 추적 | 쇼핑 검색결과 | **불가** — 크롤링뿐 |
| **판매량·매출액 추정** | 랭킹 + 리뷰수 + 트래픽 | **불가** — 크롤링뿐 |
| 리뷰 분석 | 상품 리뷰 | **불가** — 크롤링뿐 |
| 로켓상품 비율 | 쿠팡 검색결과 | **불가** — 크롤링뿐 |

**절반은 합법 API로 되고, 절반은 크롤링이 필요하다.**

## 3. 아이템스카우트의 매출 데이터는 실제 데이터가 아니다

이건 꼭 짚어야 한다. 아이템스카우트가 주는 판매량·매출액은
**실제 판매 데이터가 아니라 각 쇼핑몰의 랭킹·리뷰 수·트래픽 등 공개 데이터 기반 추정치**다.
아이템스카우트 본인들이 그렇게 밝히고 있다.

두 가지 의미가 있다.

**① 그들도 네이버가 안 주는 걸 추정으로 만든다.** 마법이 아니다.
**② 그 추정의 재료는 네이버쇼핑을 긁어서 얻는다.** 쇼핑검색 API가 종료된 지금은 더더욱 크롤링뿐이다.

앞선 검토에서 "6개월 매출·판매량·평균가격을 버린 판단이 맞았다"고 한 이유가 이거다.
**그 숫자들은 원본이 아니라 추정이었고, 원본으로 가는 합법 통로는 이미 닫혔다.**

## 4. 크롤링 — 여기서 패스가 나온다

**네이버 vs 다윈중개 (네이버페이 부동산 매물정보 무단 크롤링)**

- 법원: 반복·체계적 크롤링이 네이버의 **데이터베이스권 침해**
- 동시에 **부정경쟁방지법상 부정경쟁행위**로도 인정
- **손해배상 8,000만원 + 데이터 삭제 명령**
- 핵심 논리: **"공개된 웹사이트 정보라도 자동으로 대량 수집해 무단 사용하면 DB권 침해"**
- 네이버가 DB 구축·검증에 투입한 투자가 DB 제작자의 권리로 인정됨

네이버쇼핑도 구조가 똑같다. 상품·가격·랭킹·리뷰를 네이버가 비용 들여 모으고 검증한 DB다.
**긁어서 지표로 팔면 다윈중개 사건과 같은 그림이 된다.**

참고로 야놀자 vs 여기어때 건에서 대법원은 크롤링 접속 자체를 **컴퓨터 업무방해로는 보지 않았다.**
즉 "형법상 업무방해는 아닐 수 있으나, 저작권법상 DB권 침해와 부정경쟁행위는 별개로 성립한다"가 현재 구도다.
**형사는 피해도 민사는 못 피한다.**

여기에 2026-09-07 시행된 검색 API 특약의 **수익화 금지**가 겹친다.
API로 받아도 팔면 안 되고, 긁으면 DB권에 걸린다. **양쪽이 다 막혀 있다.**

## 5. 그래서 진짜 질문은 "가능하냐"가 아니다

**"왜 만드냐"**다. 답에 따라 판정이 완전히 갈린다.

**팔려고 만든다면 → 패스.**
- 법적 리스크가 사업 규모보다 크다
- 이미 자리 잡은 강자가 둘이고, 그들은 리스크를 감수하며 먼저 들어가 있다
- 후발주자가 같은 리스크를 지고 따라가는 건 최악의 포지션이다

**내가 쓰려고 만든다면 → 린정.**
- 비공개·본인 전용이면 수익화 조항에 안 걸린다
- 크롤링 없이 합법 API만으로 위 표의 절반은 이미 된다
- 그리고 그 절반을 **이미 만들어놨다**

## 6. 제안 — 복제하지 말고 빈칸을 쳐라

두 서비스의 **공통 약점**이 있다.

> **"팔릴까?"는 알려주는데, "얼마에 떼올 수 있나?"는 모른다.**

둘 다 수요 쪽(검색량·경쟁·순위)만 본다. 공급가는 셀러가 알아서 구해야 한다.
**그런데 형은 온그린 공급가와 KAMIS 도매시세를 붙일 수 있다. 그건 그들에게 없다.**

```
아이템스카우트 · 판다랭크
   수요(검색량 · 경쟁 · 순위)              →  "이거 팔릴까?"

슈퍼프룻
   수요 + 공급가 + 도매시세                →  "이거 남을까?"
```

**"팔릴까"에서 "남을까"로 질문을 바꾸는 것.** 이게 복제가 아닌 차별점이다.

게다가 이 방향은 크롤링이 필요 없다. 축이 전부 합법 API다.

- 수요 → 네이버 검색광고 API (본인 계정 데이터, 특약 대상 아님)
- 시즌성·추세 → API 허브
- 공급가 → 온그린 (계약 기반)
- 도매시세 → KAMIS (공공데이터)

농산물이라는 좁은 범위가 약점이 아니라 **해자**가 된다.
아이템스카우트는 전 카테고리를 얕게 훑고, 슈퍼프룻은 농산물을 마진까지 판다.

## 7. 나중에 서비스로 팔고 싶어지면

한 가지 우회로가 있긴 하다. **BYOK — 사용자가 자기 API 키를 넣는 구조.**

우리가 네이버 데이터를 받아서 재판매하는 게 아니라,
사용자가 자기 계정 데이터를 자기 화면으로 보는 도구가 된다. 성격이 달라진다.

다만 이건 **확인 필요**다. 네이버 약관이 이 구조를 어떻게 보는지,
"툴 제공 자체가 수익화인가"에 대한 해석이 필요하다. 변호사 자문 영역이다.
**지금 단계에서 이걸 전제로 설계하지는 마라.**
