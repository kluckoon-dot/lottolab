## 2. 고친 것

### 3년 그래프

- `refresh-trend.mjs` 새 옵션: `--all-section`(섹션 키워드 전부, 식품 판정과 상관없이) · `--dict-min N`(사전 키워드 검색 N↑) · `--extra 파일` · `--extra-only` · `--search-only`(쇼핑인사이트 한도를 안 씀) · `--keep-period`(받아 둔 기간 그대로, 빠진 것만) · `--refresh-days 28`(한 달에 한 번 새 주로 넘김) · `--max-calls`.
  한도 초과(429) · 서버 오류는 빈 값으로 적지 않고 멈춘다 — 전에는 실패한 묶음을 빈 값으로 적어 다시 묻지 않았다.
- 10/28 손으로: 섹션 키워드 + 사전 검색 1,000↑ 중 빠진 49,090개 (검색어트렌드 약 9,800회, 쇼핑인사이트 0회).
- `build-web.mjs` 가 `naver-out/trend-fresh.json` 을 바로 읽는다(pack 은 월요일에만 다시 만들어짐). 사전 키워드 추세는 그 키워드가 든 `data-dict-N.js` 에 같이 실려, 묶음을 읽을 때 화면의 추세 자료에 합쳐진다 — 화면 코드는 섹션 키워드와 똑같이 그린다.
- 네이버 데이터랩은 검색이 아주 적은 키워드에는 값을 주지 않는다. 그런 키워드는 빈 값으로 적어 두고(`KWHEAD.trNo` · 사전 묶음 `tr`), 화면이 "아직 안 받음" 과 구분해 "네이버가 3년 값을 주지 않는다" 고 말한다.
- 같은 날 오후 사전 검색 300↑ 도 채웠다(4.2만 개 · 약 8,300회). 검색 300 아래 사전 키워드는 종합 차트의 **3년 그래프 받아 오기** 단추로(다음 날 아침).
- 매일 수집 5단계: 섹션 전부 + 사전 300↑ + 찾아본 키워드 중 새로 들어온 것의 추세를 채운다(같은 기간). 한 달에 한 번(받아 둔 기간 끝이 28일 넘게 뒤처지면) 새 주까지로 넘겨 전부 다시 — 약 11만 개 = 약 22,700회, 하루 상한 15,000회라 이틀에 걸친다.

### 빠진 키워드

- 매일 수집 2단계에 `fetch-related-more.mjs --min 10 --max-age 7` 을 더했다 — 신선식품 키워드 중 검색 10~99 도 씨앗으로 묻는다(각 키워드 일주일에 한 번). 10/28 첫 회차 15,442개.
- **찾아본 키워드 받아 오기.** 저장본(claude.ai 페이지)은 네이버를 부를 수 없다. 그래서 페이지에서 찾았는데 받아 둔 목록 어디에도 없는 키워드는 아티팩트 데이터 `requests` 에 적힌다(정확 검색 · 여러 개 찾기 모두). 매일 아침 예약 회차가 그 목록을 `naver-out/requests.txt` 로 옮기고, `fetch-requests.mjs` 가 키워드도구에 직접 물어 값 · 연관 목록(묶음 7 "찾아본 키워드")을 받고, 3년 추세도 받는다. 결과로 상태를 바꾼다: 받을 차례 · 받아 옴 · 네이버에도 없음. 수집 현황 탭에 목록이 나온다.
  3년 그래프만 없는 키워드는 종합 차트의 **3년 그래프 받아 오기** 단추로 같은 목록에 넣는다.
- 여러 키워드 찾기가 섹션 밖 사전을 보지 않아, 사전에 있는 키워드도 "없는 것" 으로 나왔다 → 사전 묶음을 읽어 넣는다.

고친 것

- **3년 추세를 화면 파일 뒤로.** `refresh-trend.mjs` 는 화면 자료(data-kw · data-dict)에서 대상을 고르는데, bat 이 화면 파일을 만들기 전에 불러서 그날 새로 들어온 키워드(10/29: 22,542개)는 하루를 기다렸다. 이제 5 화면 파일 → 6 3년 추세 → 화면 파일 다시. 10/29 은 손으로 이어 받았다(4,509회 · 7.9분 · 실패 0).
- **저장본 256MB 한도.** 한 버전이 담는 크기가 256MB 인데 10/29 자료가 304MB(연관 목록 묶음 199MB + 사전 묶음 81MB + 나머지)라 올리기가 중간에 거부됐다. `pack-z.mjs` 가 두 묶음을 gzip + base64 글자 파일 `z/*.txt` 로 줄인다(267MB → 113MB, 올릴 것 모두 136.5MB). 저장본은 .bin 같은 이진 파일을 받지 않아 base64 로 적는다. 화면(`partLoad`)은 https 로 열리면 .txt 를 받아 풀고(DecompressionStream), PC 에서 열면 원래 .js 를 읽는다. 올린 파일을 다시 받아 PC 파일과 sha256 이 같은 것을 확인했다.
- **올리기 계획** `publish-plan.mjs`: 올라간 파일 목록을 주면 64MB · 255개 아래 묶음을 짜고, 이제 안 쓰는 옛 data-rel · data-dict .js 를 null 로 뺀다. data-head.js 는 마지막. 예약 작업 지침이 이것을 쓴다.
- 월요일 `4 정기 수집.bat`: 쇼핑 클릭 추세(4/4)를 받은 뒤 화면 파일을 다시 만들지 않아 다음 날에야 보였다 → 화면 파일 + 묶음 줄이기를 다시 부른다.

API HUB 검색어트렌드 10월 사용: 약 2.3만 + 10/29 4,509 ≈ 2.8만(무료 3만 안). 남은 10월 매일 회차는 새로 들어온 키워드만이라 하루 몇백 ~ 몇천 회 — 3만을 넘으면 한시 무료(5만) 구간이다.

## 3. 매일 수집 순서 (5 매일 수집.bat)

1 품목 목록 → 2 키워드별 목록(100↑ 매일 · 10~99 주 1회) + 품목 이름 사전(주 1회) + 조합 키워드(하루 6,000회) → 3 찾아본 키워드 → 4 목록 밖 키워드 → 5 화면 파일 → 6 3년 추세 → 화면 파일 다시 → 묶음 줄이기(z/*.txt). 약 2~3시간.
검색광고 API 는 한 계정에서 동시에 여러 갈래로 부르면 갈래마다 느려진다(10/28: 세 갈래일 때 목록 받기가 분당 250 → 50). 단계는 차례로 돈다.

## 4. 저장본이 10/22 에서 멈춰 있던 까닭

예약 회차는 올리기 전에 올라가 있는 파일 목록(list)만 봤다. 그런데 다른 세션이 올린 파일은 목록만 봐서는 "본 적 없는 새 내용" 이라 덮어쓰기가 거부된다 — 파일을 read(paths, 한 번 64MB)로 읽어야 한다. 예약 작업 지침에 그 순서를 넣었다. 10/28 회차는 결과 읽기 PowerShell 권한 확인에서 2시간 넘게 멈춰 로드가 멈추고 손으로 올렸다.
