# 실데이터 연동 계획

2026-09-10 · 프로토타입 `prototype/keyword-lab.html`을 실데이터로 바꾸는 작업 사양

---

## 먼저 — 여기서는 못 가져온다

이 작업 환경은 외부 네트워크가 정책으로 막혀 있다. `chatgpt.com`, `dhlottery`,
`ncloud.com`, 형이 준 배포 사이트까지 전부 프록시가 403으로 끊었다.
**NAVER API도 여기서는 호출할 수 없고, 나는 형의 API 키도 갖고 있지 않다.**

그래서 실데이터 연결은 **형 로컬 세션에서** 해야 한다.
이 문서는 그때 그대로 쓰는 설계서다. 프로토타입의 데이터 모델은 이미 이 구조에 맞춰 짜놨다.

| 소스 | 필요한 것 | 발급처 |

| 검색어트렌드 | 클라이언트 ID / Secret | 개발자센터 (2027-06-30) → **API 허브 권장** |

## 2. 검색광고 API — 화면 지표의 8할이 여기서 나온다

인증은 요청마다 서명을 만드는 방식이다.

```
X-Timestamp   : 밀리초 epoch
X-API-KEY     : 액세스 라이선스
X-Customer    : CUSTOMER_ID
X-Signature   : HMAC-SHA256(비밀키, `${timestamp}.${method}.${path}`) → Base64
```

**필요한 엔드포인트 두 개**

| 용도 | 엔드포인트 | 얻는 것 |
|---|---|---|
| 키워드 지표 | `/keywordstool` | 월 검색수 PC/모바일, 월평균 클릭수, CTR, 경쟁정도, 광고 노출 깊이, 연관 키워드 |
| 순위별 입찰가 | `/estimate/average-position-bid/keyword` | **1~3위 노출에 필요한 입찰가 (PC/모바일 각각)** |

> 필드명과 경로는 통용되는 값으로 적었다. **첫 실호출로 반드시 확정해라.** → 확인 필요
> 특히 입찰가 API는 device를 PC/MOBILE로 나눠 두 번 호출해야 할 수 있다.

**화면 필드 매핑**

| 프로토타입 필드 | 출처 |
|---|---|
| `pc` / `mo` | 월 검색수 PC / 모바일 |
| `bid1pc` / `bid1mo` | 1위 평균 입찰가 PC / 모바일 |
| 2위·3위 입찰가 | 같은 API를 순위 2, 3으로 호출 (지금은 1위 × 0.78 / × 0.61로 추정 중 — **반드시 실값으로 교체**) |
| `depth` | 광고 노출 깊이 |
| 경쟁강도 | 광고 깊이 + 1위 입찰가로 산출 (상품수 원본 없음) |

**연관 키워드가 탐색의 입구다.** 품종명을 `/keywordstool`에 넣으면 연관 키워드가 딸려 나온다.
지금 프로토타입이 `못난이`·`선물세트` 같은 접미사로 만들어내는 부분을 **그 응답으로 갈아끼우면 된다.**
그러면 키워드 수가 형이 원한 규모로 자동으로 불어난다.

## 3. 검색어트렌드 · 쇼핑인사이트

- **3년 추세** → 검색어트렌드. 상대지수로 오므로 절대 검색수는 검색광고 API 값으로 스케일을 잡는다.
  **절대값을 만들어내지 마라.** 화면에 "상대지수 기반 환산"이라고 적는다.
- **연령 · 성별 · 기기 구성** → 쇼핑인사이트. **카테고리 ID가 정확해야 한다.**
  `docs/03-action-guide.md`의 1순위 작업이 끝난 뒤에 붙여라. 안 그러면 전부 식품 전체 데이터가 들어온다.
- 개발자센터 키는 2027-06-30까지다. **API 허브로 먼저 붙이는 게 낫다** (한시 무료).

## 4. 저장 설계 — 약관 때문에 두 층으로 나눈다

개정 검색 API 특약이 **서버 보관 최대 21일**이다. 3년 추세를 쌓는 것과 충돌한다.
적용 범위는 확인이 필요하지만, 걸린다고 가정하고 설계해두는 게 안전하다.

```
원본층   NAVER 응답 그대로          보관 21일, 순환 삭제
파생층   황금점수 · 경쟁강도 · 시즌 · 판정   무기한 보관
```

**파생 지표는 우리가 만든 값이라 우리 자산이다.** 판정 기록도 여기 쌓인다.
원본이 지워져도 판정 이력은 남는다. 이게 `docs/05-weapon-spec.md`의 피드백 루프를 지킨다.

## 5. 하루 두 번 갱신 — 08:00 / 20:00 KST

```
cron  0 23 * * *   (= 08:00 KST)
cron  0 11 * * *   (= 20:00 KST)
```

**두 번의 성격을 다르게 가져가라.**

| 시각 | 하는 일 |
|---|---|
| **08:00 아침** | 공급사 공급가 · 재고 갱신 → 마진 재계산 → **판정 갱신** → 오늘 들어갈 품목 TOP 10 확정 |
| **20:00 저녁** | 검색광고 지표 · 입찰가 갱신 (하루 경쟁 반영) → 내일 후보 큐 준비 |

공급가는 아침에 봐야 그날 발주에 쓴다. 검색·입찰가는 하루 치가 쌓인 저녁이 낫다.

**한도 관리**
- 서비스별 하루 1,400회는 자체 설정값이다. 네이버 실제 한도를 확인하고 올릴 여지를 봐라. → 확인 필요
- 회차마다 전체를 돌지 마라. **우선순위 큐**로 돌린다.
  1. 시즌 진입 · 공급 중 품종 (매회)
  2. 판정이 린정·반린정인 키워드 (매회)
  3. 나머지 (순환, 며칠에 한 바퀴)

  수확 캘린더가 이미 있으니 1번 필터가 공짜다. 비시즌 품종에 호출을 쓰지 마라.

**실패 처리**
- 한도 초과 → 다음 회차로 이월, 화면에 "대기 N건" 표시
- 부분 실패는 부분 실패로 기록해라. 이전 값으로 덮어 성공처럼 보이게 만들지 마라
- 각 값에 **조회 시각**을 붙여 저장한다. 화면에 그대로 노출한다

## 6. 공급사 연동 — 네이버가 끝난 뒤

형이 공급사별 오픈 API와 공급가 엑셀을 주면 그때 붙인다. 준비해둘 것은 셋이다.

**① 두 경로를 모두 받는다**
```
공급사 API  →  자동 갱신 (있는 업체)
엑셀 업로드 →  수동 갱신 (없는 업체)
```
둘을 같은 테이블에 넣되 `source`와 `updatedAt`을 남긴다. 화면에서 자동/수동을 구분해 보여준다.

**② 규격 정규화가 진짜 일이다**
`2kg 중과`, `5kg 대과`, `2통`, `500g` — 업체마다 표기가 다르다.
**kg 단가로 환산해야 비교가 된다.** 파싱 실패하면 비교에서 빼고 "규격 미확인"으로 표시해라.
억지로 맞추면 틀린 비교가 나온다.

**③ 발주·결제는 아직 붙이지 마라**
`docs/04` 판정 그대로다. 공급가 조회부터 실호출로 검증하고, 발주는 그 다음이다.
결제 자동화는 최소 6개월 뒤 얘기다.

## 7. 순서

```
0.  카테고리 ID 버그 수정            ← 이거 먼저. 안 하면 쇼핑인사이트가 전부 오염
1.  검색광고 API 실호출 1건          ← 필드명·입찰가 API 스펙 확정
2.  연관 키워드로 키워드 풀 확장      ← 여기서 규모가 폭발한다
3.  프로토타입 데이터 모델에 실값 주입
4.  2·3위 입찰가 실값으로 교체       ← 지금은 추정 배율
5.  검색어트렌드 → 3년 추세
6.  쇼핑인사이트 → 연령·성별·기기     ← 0번 끝난 뒤에만
7.  KAMIS → 도매 시세
8.  08:00 / 20:00 스케줄러 + 우선순위 큐
9.  판정 기록 테이블
10. 공급사 API (형이 자료 준 뒤)
```

## 내가 할 수 있는 것 / 못 하는 것

**할 수 있다**
- 프로토타입 화면·판정 엔진·마진 계산 (완료)
- 위 사양대로 연동 코드 작성 — 형이 응답 샘플 한 건만 붙여주면 파서까지 만든다
- 스케줄러·큐·저장 구조 설계와 구현
- 형 로컬 세션에 넣을 작업 지시문

**못 한다**
- 여기서 NAVER API 호출 (네트워크 차단 + 키 없음)
- 형 서버에 배포
- 실제 수치 검증 — 첫 응답은 형이 확인해줘야 한다

**그래서 다음 한 걸음은 이거다.**
`/keywordstool`에 아무 키워드나 하나 넣고 **응답 JSON을 그대로 붙여줘.**
그러면 그 구조에 맞춘 파서와 매핑 코드를 바로 짜서, 프로토타입의 샘플 생성기를 실데이터로 교체한다.
